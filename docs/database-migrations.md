# D1 マイグレーションと Queue メッセージの変更

マイグレーションは `migrations/` に置き、リポジトリのルートで当てる。

```bash
npm run db:migrate        # 本番の D1
npm run db:migrate:local  # ローカルの D1
```

## 新旧が混ざっても壊れないようにする

Worker のデプロイと D1 のマイグレーションは同時には反映できない。
Deploy ワークフローではマイグレーションを当ててから Worker をデプロイするので、そのあいだは古いコードが新しいスキーマの上で動く。
3 つの Worker はそれぞれ別にデプロイされ、同じ Worker でも新旧の版が一時的に並んで動く。

そのため、スキーマの変更は Expand / Contract に分け、どの組み合わせの版が動いても壊れないようにする。
本当に守る必要があるのは「新しいコードが、まだ追加されていないカラムを読まないこと」と
「古いコードが使っているカラムを消さないこと」の 2 つ。

### Expand

- 追加だけのマイグレーションを先に当てる。追加するカラムは NULL 可かデフォルト付きにする。新しいテーブルの追加もここに入る。
- 新しいカラムを読むコードは、マイグレーションを当てたあとのデプロイで出す。
- 既存データの埋め戻しはマイグレーションのファイルと分ける。小分けにして、何度実行しても同じ結果になる形で行う。

### Contract

- 古いカラムを使うコードがなくなってから、別のデプロイでそのカラムを削除する。
- リネームは「新しいカラムを追加 → 両方に書き込む → 読み取りを新しいカラムに切り替え → 古いカラムを削除」に分け、それぞれ別のデプロイで出す。
- デフォルトなしの NOT NULL カラムを追加しない。
- D1 は SQLite なので、カラムの型を変えるときは新しいテーブルを作ってデータをコピーする。

## Queue メッセージの形式

Queue（`hn-processor`）のメッセージは backend-worker の poller と admin-worker が送り、backend-worker の processor が受け取る。
送る側と受け取る側の版が混ざるうえ、再試行中のメッセージは古い形式のままキューに残る。
メッセージの形式を変えるときは、古い consumer が新しいメッセージを受け取っても、新しい consumer が古いメッセージを受け取っても壊れないようにする。
フィールドの追加と削除は、スキーマと同じく Expand / Contract に分ける。

## 戻すとき

Expand / Contract を守っていれば、不具合はコードを戻すだけで直せる。スキーマを戻す必要はない。

最後の手段として D1 Time Travel でデータベースを過去の時点に戻せる。
戻せるのは Free プランで 7 日、Paid プランで 30 日前まで。
指定した時刻より後の書き込みはすべて消える。

```bash
npm -w feed exec -- wrangler d1 time-travel restore hn-feed --timestamp=<時刻>
```
